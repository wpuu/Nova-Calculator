## A. 问题1：圆圈点击坐标偏移

### 根因结论
**部分确认（逻辑层已确认 / 偏移量级与方向需真机验证）。**

实际源码证据：
- `AutoClickerService.java` `clickRunnable`（L493-516），点击坐标计算（L507-509）：
  ```java
  int cx = paramsArr[idx].x + circleSizePx / 2;
  int cy = paramsArr[idx].y + circleSizePx / 2;
  dispatchClick(cx, cy);
  ```
- `createAndAddOverlay()`（L331-356）：窗口 `paramsArr[index].width/height` 被强制设为 `circleSizePx`（L343-344），初始 `x/y` 由 `screenW/screenH` 推算（L345-352）。`baseParams()` 使用 `gravity = TOP | START`（L381-390）。
- `auto_clicker_circle.xml`：根 View 即 `ImageView`（id `auto_clicker_reticle`），宽高 26dp，`scaleType=fitCenter`。
- `AutoClickerReticle.onDraw()`（L74-92）：圆环与中心点绘制在 `w/2, h/2`（即窗口几何中心）。
- `dispatchClick()`（L518-525）用 `dispatchGesture`，其坐标属于**当前 display 坐标系**。

**已确认的逻辑缺陷**：点击点由「缓存的 `paramsArr[idx].x/y` + 固定 `circleSizePx/2`」推算，而非读取 View 在屏幕上的真实位置。该算法隐含两个假设：① `params.x/y` 等于窗口在屏幕坐标系中的左上角；② 圆环正好落在窗口几何中心且窗口无额外 inset。这两个假设在 `TYPE_ACCESSIBILITY_OVERLAY` 下不一定成立（系统可能对无障碍overlay窗口施加与 `params` 不同的坐标/inset处理；刘海、状态栏、display area 也可能引入偏移），从而导致点击点偏到圆环上方/圈外——与用户观测一致。

**需真机验证**：偏移的具体方向与量级（仅从源码无法判定 `params.x/y` 与 `getLocationOnScreen()` 在 EMUI/特定 ROM 上相差多少）。

### 风险评级
**中**（功能可用但点击落点错误，连点打不准）。不阻断编译/启动。

### 最小修改方案
文件：`AutoClickerService.java`
方法：`clickRunnable`（L504-511 区块）

修改前（L507-509）：
```java
int idx = targetIndex;
int cx = paramsArr[idx].x + circleSizePx / 2;
int cy = paramsArr[idx].y + circleSizePx / 2;
dispatchClick(cx, cy);
```

修改后：
```java
int idx = targetIndex;
if (!overlayReady || overlayViews[idx] == null
        || !overlayViews[idx].isAttachedToWindow()) {
    return; // 圆圈未就绪/已移除，跳过本次点击
}
View v = overlayViews[idx].findViewById(R.id.auto_clicker_reticle);
if (v == null) v = overlayViews[idx];
int[] loc = new int[2];
v.getLocationOnScreen(loc);
int w = v.getWidth();
int h = v.getHeight();
if (w <= 0 || h <= 0) return;
int cx = loc[0] + w / 2;
int cy = loc[1] + h / 2;
dispatchClick(cx, cy);
```
（保留 `targetIndex = (targetIndex + 1) % overlayViews.length;` 不变）

### 边界和异常处理
- **必须在主线程读取坐标**：`clickRunnable` 经 `handler`（主线程 Looper，L78、L471）调度，满足；`getLocationOnScreen` 要求在 attached View 上调用，已用 `isAttachedToWindow()` 守卫。
- **View 未 attach / width=0**：`overlayReady`、`isAttachedToWindow()`、`w<=0` 三重守卫后直接 return，不会点错位置。
- **拖动后坐标系**：`getLocationOnScreen()` 每次点击实时读取，比缓存 `params` 更准；拖动监听器（`makeTouchListener`，L392-437）更新的是 `paramsArr` 用于 `updateViewLayout`，与点击读取互不冲突。
- **屏幕旋转 / display 变化**：`getLocationOnScreen()` 读取的是当前真实屏幕坐标，`dispatchGesture` 同属当前 display 坐标系，二者天然一致；无需手动校正 density / 状态栏 / 刘海 / WindowInsets。
- **`getLocationOnScreen` vs `getLocationInWindow`**：此处要的是屏幕绝对坐标以喂给 `dispatchGesture`，必须用 `getLocationOnScreen()`（`getLocationInWindow` 对 WindowManager 窗口通常返回 ~0,0，不可用）。
- **是否需新增日志**：建议仅在 `BuildConfig.DEBUG` 下打印 `cx/cy/loc/w`，不打印任何密令/截图内容。
- **不修改**：`baseParams()`、`createAndAddOverlay()` 的圆圈尺寸与拖动逻辑保持不变；继续沿用 `TYPE_ACCESSIBILITY_OVERLAY`，**不引入 `SYSTEM_ALERT_WINDOW` 依赖**。

### 真机验证项目
1. 圆圈静止时点击是否正中红/蓝点。
2. 拖动圆圈到四角/刘海区/导航栏附近后，点击是否仍正中。
3. 屏幕旋转后首拍是否准确。
4. EMUI / 原生 ROM 下偏移是否消除。

### 回归风险
**低**。改动仅限点击坐标计算，不影响圆圈显示、拖动、开关状态机。

## B. 问题2：高级设置隐藏与 8888

### 可见入口审查
**已确认。**

- `res/menu/main.xml` L109-112：
  ```xml
  <item
      android:id="@+id/menu_hidden_settings"
      android:title="高级设置"
      app:showAsAction="never" />
  ```
  该菜单项**始终存在于选项菜单**（overflow），标题中文明示「高级设置」，任何能打开计算器选项菜单的人都能看到并点开 `SettingsActivity`。
- `CalculatorActivity.java` L291-293 的 `onMenuItemClick` 分支：
  ```java
  } else if (itemId == R.id.menu_hidden_settings) {
      startActivity(new Intent(CalculatorActivity.this, SettingsActivity.class));
      return true;
  }
  ```
- `AndroidManifest.xml` L79-80：`.SettingsActivity` 为 `android:exported="false"`，**无 LAUNCHER、无外部 intent-filter**，因此不存在 manifest 级的额外可见入口（无第二个 visible 入口）。
- 唯一「隐藏入口」是 8888 密令（见下）。

### 当前 8888 触发范围
**已确认：仅在计算器编辑器输入时有效。**

- `Keyboard.java` `onEditorChanged`（L291-334）：只有当编辑器文本变化时才检查 `text.endsWith(secretCodeSettings/secretCodeSettingsAlt)`（L328-331）并 `bus.post(SETTINGS)`。
- `CalculatorActivity.onSecretCodeEvent` 的 `SETTINGS` 分支（L366-368）`startActivity(SettingsActivity)`。
- 即：8888 仅在**计算器编辑器聚焦且输入了 8888** 时触发；App 内其它 Activity、失焦状态、系统全局均不触发。

### 是否建议全局按键监听
**不建议将 8888 做成系统全局按键拦截。**
- `AutoClickerService.onKeyEvent()`（L527-534）仅处理 `VOLUME_DOWN`，且 `FLAG_REQUEST_FILTER_KEY_EVENTS`（L129-138）在主流 ROM（尤其 EMUI、MIUI、ColorOS）上**经常收不到数字键**，也拿不到普通数字输入；强行拦截会干扰系统输入法、拨号器、其它 App 的输入，并可能违反隐蔽功能的安全边界。
- 需求「任何情况下按 8888」应落地为：**计算器 App 内任意 Activity 均可输入** 即可，不必系统全局。

### 最小修改方案
1. **删除可见菜单项（最小且不影响其它菜单）**
   - `res/menu/main.xml`：删除 L109-112 整段 `menu_hidden_settings` 项。
   - `CalculatorActivity.java` L291-293：删除 `else if (itemId == R.id.menu_hidden_settings)` 整支（保留其余菜单分支）。
   - 不采用 `visible=false` 方案（仍留在菜单定义里属冗余），直接删除最干净，且不影响 `menu_about` 等其它项。

2. **8888 触发保留并防重复启动**
   - `Keyboard.java` 现有 `SETTINGS` 派发（L328-331）**保持不变**，链路 `Keyboard → bus → CalculatorActivity.onSecretCodeEvent → SettingsActivity` 不破坏。
   - `CalculatorActivity.java` L366-368 改为加 `FLAG_ACTIVITY_SINGLE_TOP`，避免连点 8888 堆叠多个 SettingsActivity：
     ```java
     case SETTINGS: {
         Intent it = new Intent(this, SettingsActivity.class);
         it.addFlags(Intent.FLAG_ACTIVITY_SINGLE_TOP);
         startActivity(it);
         break;
     }
     ```
   - 输入 8888 后清空编辑器：现有 `Keyboard` 通过 `CLEAR_EDITOR` 事件（L286-288）已在派发后清空，无需改动；如未清空，可显式 `editor.setText("")`（注意：与现有 CLEAR_EDITOR 订阅不冲突，不重复加）。

3. **（可选，若要求「App 内任意页面」都能输 8888）**：不做系统全局监听；仅需确保 `Keyboard` 的 `onEditorChanged` 在 App 内任意带编辑器焦点的页面都生效——当前架构已满足（键盘为全局输入）。若某些子页面无编辑器，则 8888 自然不触发，属可接受边界。

### 边界和异常处理
- 删除菜单后，`SettingsActivity` 内部 `llSettings` 等「修改密令」入口仍可达（已在 SettingsActivity 内），不破坏。
- 防止 8888 被普通数字逻辑吞掉：`endsWith` 匹配（L328）只认后缀，普通计算输入不会恰好以 8888 结尾而误触发；无需改动。
- 防重复：仅 `SINGLE_TOP`，不限 `NEW_TASK`，行为自然。
- 登录/授权边界：进入 `SettingsActivity` 不新增任何权限请求，符合隐蔽功能安全边界。

### 真机验证项目
1. 选项菜单中「高级设置」项已消失。
2. 计算器输入 8888（或 `secretCodeSettingsAlt`）后进入 SettingsActivity。
3. 连续输入 8888 仅启动一个 SettingsActivity 实例（不堆叠）。
4. 其它菜单项（关于/绘图/转换等）正常。

### 回归风险
**低**。仅删除一个菜单分支 + 给 8888 启动加 SINGLE_TOP。不影响密令解析、连点、拍照/录像链路。

## C. 问题3：110 拍照失败（有反馈无照片）

### 根因结论
**已确认（源码级根因锁定）。**

实际源码证据：
- `CalculatorActivity.takeHiddenPhoto()`（L372-379）：
  ```java
  public void takeHiddenPhoto() {
      triggerHapticFeedback(1);
      flashSecretRecordingUI();                       // ← 无条件先变暗（约 2s）
      VideoRecorderManager.INSTANCE.takeHiddenPhoto(this,
          () -> {},                                  // onCaptureInitiated（此处空实现）
          () -> triggerHapticFeedback(2));           // onCaptureCompleted
  }
  ```
- `VideoRecorderManager.takeHiddenPhoto()`（L126-165），首行（L131）：
  ```kotlin
  val currentImageCapture = imageCapture ?: return   // imageCapture 为 null 时静默返回，不写文件
  ```
- `imageCapture` 仅在 `bindCamera()` 内被赋值（L49-51）；而 `bindCamera()` 唯一的调用点是 `CalculatorActivity.onCreate()`（L144-145）：
  ```java
  if (ContextCompat.checkSelfPermission(this, CAMERA) == PERMISSION_GRANTED) {
      VideoRecorderManager.INSTANCE.bindCamera(this, this, hiddenPreview);
  }
  ```
  → **首次启动未授权 CAMERA 时，`bindCamera` 永不调用，`imageCapture` 永久为 null**。此后即便用户在系统设置里授权，也没有任何回调重新 `bindCamera`。
- `flashSecretRecordingUI()`（L444-467）只负责把「擦除键」变暗 2 秒，**不验证拍照是否成功**。
- `SettingsActivity.exportEvidenceSafely()`（L231-284）只扫描 `filesDir/*.dat`；因无 `.dat` 产出 → 提示「沙盒为空」。

结论：110 收到后**视觉反馈（变暗）无条件执行**，但真实拍照因 `imageCapture == null` 静默失败 → 无文件 → 导出空。与用户现象**完全吻合**，根因源码确认。

### 风险评级
**高**（核心隐蔽取证功能失效，且「假成功」会误导用户以为已拍到）。

### 权限/绑定流程（正确目标）
```
收到 110
 -> 检查 CAMERA 权限
 -> 若未授权 / imageCapture==null：请求权限（或重新 bindCamera）
 -> 权限回调成功后 bindCamera（带 onReady 回调）
 -> 确认 imageCapture != null
 -> 执行 takePicture
 -> onImageSaved 确认 filesDir 写入成功
 -> 此时再执行「变暗反馈 / 完成震动」
 -> onError / 超时 / null：显示失败反馈（Toast），不得假装成功
```

### 成功反馈时机
**照片真正写入成功后再做「变暗/完成」反馈**；未就绪时只显示「请求权限 / 正在初始化相机」提示，绝不在拍照前无条件变暗。

### 最小修改方案
文件1：`VideoRecorderManager.kt`
- 新增就绪判断与 bind 完成回调（不重写管理器）：

  ```kotlin
  fun isVideoCaptureReady(): Boolean = videoCapture != null

  fun bindCamera(
      context: Context,
      lifecycleOwner: LifecycleOwner,
      hiddenPreview: PreviewView?,

      // 原逻辑不变；在 cameraProvider.bindToLifecycle(...) 成功后：
      //   orientationEventListener?.enable()
      //   onReady?.run()   // ← 加这一行
  }
  ```
- `takeHiddenPhoto` 增加「未就绪」分支，避免静默吞掉：

  ```kotlin
      val currentImageCapture = imageCapture ?: run { onNotReady.run(); return }
  ```

文件2：`CalculatorActivity.java`
- 新增权限 launcher（与现有 `hiddenPreview` 复用）：
  ```java
  private boolean pendingPhoto = false;
  private final ActivityResultLauncher<String> cameraPermLauncher =
      registerForActivityResult(new ActivityResultContracts.RequestPermission(), granted -> {
          if (Boolean.TRUE.equals(granted)) {
              VideoRecorderManager.INSTANCE.bindCamera(this, this, hiddenPreview,
                  () -> { if (pendingPhoto) { pendingPhoto = false; takeHiddenPhoto(); } });
          } else {
              Toast.makeText(this, "相机未授权，无法拍照", Toast.LENGTH_SHORT).show();
          }

  ```
- 改写 `takeHiddenPhoto()`：
  ```java
  public void takeHiddenPhoto() {
      if (!VideoRecorderManager.INSTANCE.isImageCaptureReady()) {
          pendingPhoto = true;
          if (ContextCompat.checkSelfPermission(this, Manifest.permission.CAMERA)
                  != PackageManager.PERMISSION_GRANTED) {
              cameraPermLauncher.launch(Manifest.permission.CAMERA);
              Toast.makeText(this, "正在请求相机权限…", Toast.LENGTH_SHORT).show();
          } else {
              // 已授权但未绑定（首次启动前未授权场景）：补绑
              VideoRecorderManager.INSTANCE.bindCamera(this, this, hiddenPreview,
                  () -> { if (pendingPhoto) { pendingPhoto = false; takeHiddenPhoto(); } });
          }
          return;
      }
      triggerHapticFeedback(1);
      // 把「变暗反馈」放到真正开始拍照时（onCaptureInitiated），而非拍照前
      VideoRecorderManager.INSTANCE.takeHiddenPhoto(this,
          () -> flashSecretRecordingUI(),
          () -> { triggerHapticFeedback(2); /* 可选：Toast "已取证" */ },
          () -> Toast.makeText(this, "相机未就绪", Toast.LENGTH_SHORT).show());
  }
  ```

### 边界和异常处理
- **首次授权后无回调问题**：原代码只在 `onCreate` 判断一次；新增 launcher 在用户授权后 `bindCamera` 并 `onReady` 重试，根治。
- **权限弹窗返回时序**：`bindCamera` 内部 `cameraProviderFuture` 为异步；用 `onReady: Runnable` 在 `bindToLifecycle` 成功后触发，避免竞态（110 早于绑定完成触发）。
- **无预览拍照**：`hiddenPreview` 为 null 时 `preview.setSurfaceProvider` 被跳过（L45-47），`imageCapture` 仍可绑定，隐藏拍照可行；是否允许无预览由 ROM 决定 → 真机验证。
- **相机被其它 App 占用**：`bindToLifecycle` 抛异常会被现有 `catch`（L84-86）吞掉且 `imageCapture` 可能为残值；建议在 `catch` 里 `imageCapture=null; videoCapture=null;` 并在 `onNotReady` 反馈。
- **文件落盘确认**：`sys_img_$ts.dat` 写入 `filesDir`，导出逻辑 `name.contains("img")→.jpg`（SettingsActivity L245-249）一致。
- **日志**：`onError` 用 `Log.e("CameraX", "...", exc)` 属正常诊断，不打印照片内容/密令。

### 真机验证项目
1. 首次未授权启动 → 输 110 → 弹权限 → 授权后是否真出 `.dat` 并导出成功。
2. 已授权启动 → 输 110 → 是否立即出片。
3. 110 后「变暗」是否只在拍照真正开始时出现（而非假成功）。
4. 相机被其它 App 占用时是否给出失败提示而非静默。
5. 锁屏/后台 `CameraX` 是否可用（ROM 相关）。

### 回归风险
**中**。改动涉及权限 launcher 与 `bindCamera` 签名新增可选参数（默认 `onReady=null`，旧调用点 `L145` 仍可编译）。需确认 `hiddenPreview` 变量在 `CalculatorActivity` 中可见（现有 `bindCamera(this,this,hiddenPreview)` 已引用，存在）。

## D. 问题4：112/113/114/115、8888、音量键

### 录像/录音（112/113/114/115）
**根因确认（与 110 同源）。**

- `VideoRecorderManager.startHiddenVideoRecording()`（L90-116）首行：
  ```kotlin
  val currentVideoCapture = videoCapture
  if (currentVideoCapture == null || recording != null) return  // 静默返回
  ```
  `videoCapture` 同样只在 `bindCamera()`（L57）赋值，而 `bindCamera` 仅在 `onCreate` 授权相机时调用 → 未授权则永久 null → 112/113 静默失败。
- 关键差异：**112/113 完全没有调用 `flashSecretRecordingUI()` / `updateSecretRecordingUI()`**（对比 110 至少会无条件变暗），因此失败时**连 110 那点视觉都没有，完全无反馈**——与用户「110 之外所有快捷键都没效果」吻合。
- 录音 `AudioRecorderManager.startHiddenAudioRecording()`（L16-50）用 `MediaRecorder`，文件名 `sys_cache_$ts.dat`（L25），导出逻辑 `name.contains("img"/"vid")` 均不匹配 → 落入 `.m4a`（SettingsActivity L247），一致；但需 `RECORD_AUDIO` 权限，当前代码未在使用前显式校验权限。
- `recording != null` 守卫（L96）可防重复 start，良好；但 `stopHiddenVideoRecording`（L118-124）在 `recording==null` 时直接 return，符合预期。

最小修复：
- `VideoRecorderManager` 增加 `isVideoCaptureReady()`（见 C 节）；`startHiddenVideoRecording` 在 `videoCapture==null` 时改走 `onNotReady` 回调而非静默 return（新增可选 `onNotReady: Runnable` 参数，默认空实现）。
- `CalculatorActivity.startHiddenVideoRecording()`（L335-341）：先判 `isVideoCaptureReady()`，未就绪则请求 `CAMERA（+RECORD_AUDIO）` 并 `bindCamera(onReady)` 后重试；加 `onNotReady` 失败 Toast（如「指令未生效」，不泄露隐蔽语义）。
- 录音：`startHiddenAudioRecording()`（L381-387）增加 `RECORD_AUDIO` 权限校验，未授权则请求并 `bindCamera`/重试；失败给通用 Toast。
- **失败反馈不泄露功能**：Toast 文案用「指令未生效 / 请先授予权限」等中性表述，不出现「录像/录音/拍照」字样。

### 连点器音量键
**保留为 best-effort，不承诺全设备可用。**

实际源码：
- `AutoClickerService.requestKeyFiltering()`（L129-138）设置 `FLAG_REQUEST_FILTER_KEY_EVENTS`。
- `onKeyEvent()`（L527-534）仅处理 `VOLUME_DOWN` 且 `return true`。

风险点：
- 在 EMUI/MIUI/ColorOS 等 ROM 上，`FLAG_REQUEST_FILTER_KEY_EVENTS` **经常收不到音量键** → 用户实测「没效果」符合预期。
- `return true` 会**消费掉 `VOLUME_DOWN`**，若 ROM 真把事件送达，会导致系统音量下键失效（安全/UX 隐患）。

处置建议（按用户优先级）：
1. **保留 FLAG 作为 best-effort**，但不依赖它；保留 `onKeyEvent` 逻辑。
2. **可靠入口优先用 App 内软触发**：圆圈 `OnTouchListener` 已在 `ACTION_UP` 检测「短按 + 位移小」时 `toggleClicking()`（L424-431），该软触发在所有 ROM 都可用——这是首选开关方式。
3. 若担心 `return true` 吞掉系统音量，可在用户明确需要时才启用音量键，或在文档中标注「音量键仅部分机型有效」。不建议为「所有设备可用」而强行全局拦截。
4. 日志：在 `onKeyEvent` 内加 `BuildConfig.DEBUG` 下 `Log.d("AutoClickerKey","VOLUME_DOWN")` 即可，不打密令。

## E. 统一状态与权限建议

- **`pendingHiddenAction` 是否需要**：建议用**分散的 pending 标志**（`pendingPhoto` / `pendingVideo` / `pendingAudio` boolean）即可，不必引入统一枚举状态机；每个动作在权限 `onReady` 后只重试自己那一个，避免互相干扰。若后续动作增多，再抽象 `SecretAction` 枚举。

- **错误反馈**：所有 `imageCapture/videoCapture==null`、`onError`、权限拒绝都必须有**中性 Toast**（如「指令未生效 / 权限未授予」），**绝不允许静默吞掉**，也**不允许用 UI 反馈冒充成功**。
- **日志策略**：统一 `BuildConfig.DEBUG` 守卫；只记录「事件类型 / 是否匹配 / 相机就绪态 / 错误类」，打印密令原文、照片或音频内容属**禁止**。生产包 `DEBUG=false` 时不输出任何敏感日志。
